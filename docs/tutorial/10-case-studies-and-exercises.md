# 第 10 章　案例研究與練習

> 本章目標：從這個專案實際發生過的 bug 學習——它們怎麼逃過測試、怎麼被發現、怎麼重現、怎麼修；最後提供一組由淺入深的練習題，讓你動手延伸系統。

---

## 10.1 案例研究

以下案例都真實發生過，完整紀錄在 `docs/test-report.md` 第 5、10 節與對應的 commit。

### 案例 1：當機留下的日誌讓檔案打不開

| 項目 | 內容 |
|---|---|
| 症狀 | 程式在寫入途中被強制結束後，再開檔顯示「賽事檔已損毀或無法讀取：賽事檔為唯讀，無法寫入」 |
| 為什麼測試沒抓到 | 測試涵蓋了「損毀」「版本過新」等情境，但沒有「交易進行到一半當機」 |
| 根因 | 開檔前的檢查使用唯讀連線；唯讀連線無法用熱日誌回復，SQLite 回傳 `SQLITE_READONLY_ROLLBACK`（776），被歸類為損毀 |
| 修正 | 唯讀錯誤且有 `-journal` 時判為 `NeedsRecovery`；持有鎖定後用讀寫連線讓 SQLite 回滾，再重新檢查；通知使用者 |
| Commit | `bab9aa8` |

**教訓**：

1. **重現測試要先證明前提成立**。第一版重現測試資料量太小，交易還沒把資料頁寫回主檔，日誌不是「熱」的——測試在測一個不存在的情境。修正後的測試先斷言「日誌存在」「主檔已被改動」，才去驗證回復。
2. **錯誤分類要精確**。「唯讀錯誤」有很多種原因，把它們全部當成「損毀」，就會對使用者說謊。
3. **「檢查」與「修改」要分開**。檢查可以隨時做；回復會寫入檔案，只能在持有鎖定後做。

### 案例 2：正常退賽被誤判為「過期」

| 項目 | 內容 |
|---|---|
| 症狀 | 第 4 輪發布後，某選手退賽，第 4 輪立刻顯示「過期」，提示裁判重新配對 |
| 為什麼測試沒抓到 | 過期判定的測試都是「更正成績」的情境，沒有「發布後退賽」 |
| 根因 | 判定第 k 輪時用「目前的參賽者」重算，退賽者已不在名單中，建議自然不同 |
| 修正 | `AsAtPublication`：出現在該輪引擎建議中、退賽生效輪 ≤ k 的選手，判定時視為仍在籍 |
| Commit | `ba1c5b2` |

**教訓**：

1. **一個功能的「輸入」可能被其他功能改變**。過期判定的輸入包括「參賽者名單」，而退賽、遲到加入都會改變它。設計時列出「哪些操作會影響這個功能的輸入」，逐一確認語意。
2. **修正後要防止修過頭**。另外加了一個測試：退賽之後再更正成績，系統仍要正確判定為過期——確保「退賽豁免」沒有把真正的過期也藏起來。

### 案例 3：過期判定讓 CPU 持續滿載

| 項目 | 內容 |
|---|---|
| 症狀 | 400 人 9 輪時，每登錄一個成績，背景就重算約 5 秒，CPU 持續滿載 |
| 為什麼測試沒抓到 | 效能測試只測「產生一輪配對」，沒測「過期判定」 |
| 根因 | 每次狀態改變都對所有已發布輪次重跑引擎 |
| 修正 | 以「各輪輸入的指紋」快取引擎建議（引擎是輸入的純函式，快取精確）；登錄最後一輪成績降到約 8 ms |
| Commit | `e5f7501` |

**教訓**：

1. **效能需求要涵蓋所有「自動觸發」的計算**，不只是使用者按按鈕的那些。
2. **純函式可以安全快取**；快取正確性用「有快取 = 無快取」的性質測試保證。
3. **指紋要涵蓋所有會影響結果的輸入**，漏一項就會回傳過時的結果。

### 案例 4：不穩定的 UI 測試

| 項目 | 內容 |
|---|---|
| 症狀 | 一個 UI 測試約每 8 次失敗 1 次 |
| 第一次修法 | 拉長等待時間——無效 |
| 根因 | bUnit 的 `WaitForAssertion` 只在元件重繪時重新檢查；被測元件不訂閱 `Changed`，背景判定若在首次渲染後才完成，就不會再檢查 |
| 修正 | 測試直接 `await` 背景判定完成後再渲染 |
| Commit | `f1c4ef6` |

**教訓**：不穩定的測試一定有根因。讀失敗訊息（「Check count: 1」）比調參數有用得多。

### 案例 5：INSERT OR REPLACE 刪掉別的選手

| 項目 | 內容 |
|---|---|
| 症狀 | 寫入一位選手時，若註冊編號與另一位衝突，另一位選手整列消失，且不報錯 |
| 根因 | SQLite 的 `REPLACE` 遇到任何 `UNIQUE` 衝突都會先刪除衝突列 |
| 修正 | 改為 `INSERT ... ON CONFLICT(id) DO UPDATE` |
| Commit | `5e6652f` |

**教訓**：資料庫語法的語意要查清楚。`REPLACE` 聽起來像「更新」，實際上是「刪除再插入」。

### 案例 6：列印時印出不該印的面板

| 項目 | 內容 |
|---|---|
| 症狀 | 列印草稿輪次的對戰表時，「與最佳解比較」面板與頁首一起印出 |
| 為什麼測試沒抓到 | 自動測試看不到列印結果 |
| 發現方式 | 實機開啟 WebView2 列印預覽 |
| 修正 | 面板標為 `screen-only`；列印時隱藏頁首；加回歸斷言 |
| Commit | `4554dc9` |

**教訓**：自動測試無法取代所有實機驗證。列印、視窗、缺少執行環境這類情境，要列入手動驗證清單（`docs/test-report.md` 第 8 節）。

### 案例 7：違反自己訂的規則

- 舊版升級的備份檔名用了 `DateTime.Now`，違反「時間一律由 `TimeProvider` 注入」（`ac55bec`）。
- 決策 Q8「用測試強制禁止浮點數」在設計文件裡寫了，卻漏做了（`ac55bec`）。

**教訓**：規則如果沒有自動檢查，就會被忘記。定期把設計文件與實作對照一次；能寫成測試的規則就寫成測試。

## 10.2 從案例歸納的檢查清單

設計一個功能時問自己：

- [ ] 這個功能的**輸入**可能被哪些其他操作改變？語意都對嗎？
- [ ] 中途當機、取消、斷線時會怎樣？
- [ ] 這個計算會**自動觸發**嗎？最壞情況要多久？
- [ ] 錯誤訊息對使用者說的是實話嗎？
- [ ] 使用者確認後到實際執行之間，狀態可能改變嗎？
- [ ] 有哪些情境自動測試看不到，需要實機驗證？

寫重現測試時問自己：

- [ ] 我有沒有先看到它失敗？
- [ ] 測試的**前提條件**有斷言嗎？
- [ ] 修好後，有沒有一個「防止修過頭」的測試？

## 10.3 練習題

由淺入深。每題都先寫測試，再實作。

### 入門

1. **修改賽事名稱**：新增 `RenameTournament` 命令（第 3 章 3.9 節有完整步驟）。確認可以復原，異動紀錄正確，並把它加入 `RandomOperations`。

2. **新的結果類型**：假設要支援「延賽」（這桌改天再下，目前不計分）。思考：
   - `Round.IsCompleted` 該不該把延賽視為「已有結果」？這會影響能不能產生下一輪、自動備份、虛擬對手公式中的「已完成輪數」。
   - 同分判定與 `ScoreSheet` 要怎麼處理延賽？
   - `GameResult` 的整數值存在資料庫裡，新增列舉值時要注意什麼？（提示：不要改動既有值的順序；`StateHasher` 也用整數值。）

3. **積分榜匯出新增欄位**：在 CSV 匯出中加入「先手次數」。這個值應該在哪一層計算？

### 進階

4. **新的同分判定項目**：在 ⑥ 勝場數之後加入 ⑦「後手勝場數」。
   - 修改 `PlayerMetrics` 與 `StandingsCalculator.CriterionValues`。
   - 補一個手算範例：兩人前六項都相同，⑦ 分出高下。
   - 確認既有的性質測試（登錄順序無關、半分守恆）仍然通過。

5. **配對規則調整**：假設要加入「盡量不要讓同一所學校的選手對戰」，優先順序在 ① 與 ② 之間。
   - 選手要新增「學校」欄位：狀態、雜湊、資料庫（需要 schema 遷移 v2 → v3！）、CSV 匯入都要改。
   - 在 `PrimaryCosts` 中加入新的權重，重新推導支配關係（第 4 章 4.4 節）。
   - 參考解（窮舉與 DP）也要同步加入這條規則——並且保持它們不呼叫 Core。

6. **schema 遷移**：完成練習 5 的資料庫部分。寫一個測試：用 v2 的檔案開啟，確認先備份、再升級、資料完整、新欄位有預設值。

### 挑戰

7. **跨關檔的復原**：目前復原只在記憶體（決策 Q1）。如果要讓關檔後重開還能復原，你會怎麼設計？比較兩種方案：(a) 把歷史快照存進檔案；(b) 從 `audit_log` 反推。各有什麼問題？（提示：考慮檔案大小、相容性、`audit_log` 記錄的是給人看的文字而不是結構化資料。）

8. **增量式過期判定**：目前的快取讓「輸入沒變的輪次」不用重算，但「更正第 1 輪」時仍要重算後面所有輪次。能不能在第 k 輪的建議沒有改變時，提前判斷第 k+1 輪也不會變？（提示：第 k+1 輪的輸入取決於第 k 輪「已發布的配對與成績」，而不是第 k 輪的建議。想清楚再動手。）

9. **雙淘汰賽制**：設計敗部籤表。`KnockoutSource` 的 DAG 模型能直接表達嗎？`Normalize`、`DependentMatches`、`KnockoutStandings` 各需要怎麼改？版面計算（兩棵樹加一場總決賽）又要怎麼處理？

10. **效能分析**：用 `dotnet-trace` 或 Visual Studio Profiler 分析 500 人的配對。時間主要花在哪裡？第一階段還是第二階段？分段次數與 `WeightBitBudget` 有什麼關係？試著調整並用效能測試確認改善，同時確認 600 組窮舉比對仍然通過。

## 10.4 結語

回顧整份教學，TourneyDesk 反覆使用的幾個想法：

1. **把純邏輯與 I/O 分開**：配對、排名、鎖定規則、版面計算都是 Core 中的純函式，所以能被大量測試。
2. **不可變狀態**：復原、差異寫入、背景計算、快取都因此變得簡單又正確。
3. **單一管線**：所有變更只有一個入口，所有保證只需要在一個地方實作。
4. **先定義「最好」，再找最佳解**：目標函數與搜尋分開，演算法可以被獨立驗證。
5. **用數學保證性質**：決定性來自唯一性；循環賽的公平性來自模運算。
6. **規則寫成測試**：架構、編碼規範、驗收標準，能自動檢查的就不要靠記憶。
7. **誠實面對錯誤**：先重現、再修正、加上防止修過頭的測試，並記錄下來。

祝你在自己的專案中用得上這些想法。
